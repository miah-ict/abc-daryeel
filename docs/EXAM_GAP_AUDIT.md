# Exam implementation gap audit

Audit date: 2026-10-12  
Scope: the supplied implementation plan compared with the current frontend, API, Drizzle schema, SQL migrations, and tests. This is an evidence report only; it does not change product code.

## Executive finding

The repository contains a useful exam prototype (academic years, assignments, draft/submit/reopen, publish, results, basic re-exam and accelerated-course behavior), but it is not yet the architecture in the plan. The largest release risks are that publishing mutates the student's current class immediately, the database permits more than one active class enrollment in the same year, and progression/course rules remain embedded in `classes`. Templates, exam onboarding, deadlines, subject-level rules/results, a real course entity, and a durable promotion ledger are absent.

## Product decisions still required (not implementation defects)

These choices must be confirmed before schema/API contracts are frozen:

1. **PASS-01:** Is passing based on overall average only, or both overall average and every subject minimum?
2. **MARK-01:** Is the configured maximum global per exam or independently set per subject?
3. **DEADLINE-01:** After the deadline, may a teacher submit with `Late`, or is submission blocked until an admin reopens it?
4. **REEXAM-01:** Does a re-exam include only failed subjects or every subject?
5. **REEXAM-02:** Does the re-exam replace the old score, combine with it, or only determine the final outcome while both attempts remain visible?
6. **PROMOTION-01:** Is promotion applied when the final exam is published or when the academic year is closed?
7. **ROUND-01:** What rounding precision/mode applies to subject scores, totals, averages, thresholds, and ranks?
8. **EMPTY-01:** Can a class/subject with zero enrolled students be “complete,” and can an exam with zero applicable students be published?

Recommended default for planning: snapshot all rules onto each exam; label late submissions rather than silently accepting them; retain both original and re-exam attempts; compute promotion eligibility on publish but apply transitions only through an explicit, idempotent year-transition action.

## Migration acceptance gates

1. Preflight reports: duplicate class names per school, unmatched/ambiguous `grade_level` mappings, duplicate active enrollments, orphan references, score bounds, and counts by school/year/exam.
2. Additive schema lands first; old columns remain readable during backfill.
3. Backfill is deterministic, rerunnable/idempotent, school-scoped, and records exceptions instead of guessing.
4. Compare source/destination counts and per-exam checksums; manually approve exceptions.
5. Enable constraints only after reconciliation; run full API/invariant/concurrency tests on a production-shaped copy.
6. Cut reads/writes to the new model, observe, then retire prototype columns in a later migration with a documented restore path.
